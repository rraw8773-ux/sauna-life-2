# Sauna Life: инструкция для LLM и разработчиков

Этот файл является главным проектным контекстом для задач вида: "создай новую страницу", "добавь компонент", "введи новую фичу", "подключи стили/скрипты". Перед началом такой задачи нужно ориентироваться на этот документ и текущие файлы в корне проекта.

Проект - статическая верстка многостраничного интернет-магазина Sauna Life на HTML, CSS и Vanilla JavaScript. Здесь нет сборщика, SCSS и frontend-фреймворков. Новые решения должны быть простыми, модульными, читаемыми и совместимыми с существующей структурой.

В папку `!FILES` залезать категорически запрещено по умолчанию. Чтобы зайти туда, что-то посмотреть, проверить или тем более отредактировать, агент обязан предварительно спросить разрешение у пользователя.

Если задача не просит явно разбирать старый код (с предварительным разрешением), работать только с актуальной корневой структурой.

## 3. Как создавать новую страницу

Новая страница создается как отдельный HTML-файл в корне проекта, например `favorites.html`.

Минимальный порядок подключения CSS:

```html
<link rel="stylesheet" href="./css/custom-normalize.css" />
<link rel="stylesheet" href="./css/global.css" />
<link rel="stylesheet" href="./css/pages/favorites.css" />
```

Правила:

- Общие стили и компоненты брать из `css/global.css`, который собирает `css/base` и `css/modules`.
- Для каждой новой страницы создать отдельный файл в `css/pages`, например `css/pages/favorites.css`.
- Не добавлять стили конкретной страницы в `css/global.css`.
- Не дублировать существующие компоненты: сначала проверить `header`, `footer`, `catalog-modal`, `mobile-menu`, `product-card`, `tabs`, `custom-dropdown`, `offcanvas`, `breadcrumbs`, `buttons`.
- Header, footer, модальное меню каталога, мобильное меню, карточки товаров и базовые кнопки переиспользовать из существующей разметки и модулей.
- Новые изображения класть в `assets/images`, новые иконки - в `assets/icons`, новые шрифты - в `assets/fonts`.

JS подключается в конце страницы. Если странице хватает общего поведения каталога, использовать:

```html
<script src="./js/main.js" type="module"></script>
```

Если нужна локальная логика страницы, создать отдельную точку входа:

```html
<script src="./js/pages/favorites.js" type="module"></script>
```

Страничная точка входа должна импортировать нужные общие модули из `js/modules` и локальные модули из `js/pages/<page-name>/`.

## 4. CSS-правила

- Методология классов - BEM: `.block`, `.block__element`, `.block--modifier`.
- Состояния обозначать через `is-*`: `.is-active`, `.is-open`, `.is-hidden`, `.is-expanded`.
- Общие переменные добавлять только в `css/base/variables.css`.
- Переиспользуемые блоки добавлять в `css/modules`.
- Стили одной страницы или уникальной секции держать в `css/pages`.
- CSS писать desktop-first, затем сужать через `max-width`.
- Основные breakpoints проекта: `1539px`, `1023px`, `767px`, `479px`.
- **Корректные медиазапросы** (использовать только их):
  - `@media (max-width: 1539px) { ... }` — десктопы и крупные планшеты
  - `@media (max-width: 1023px) { ... }` — планшеты
  - `@media (max-width: 767px) { ... }` — мобильные телефоны
  - `@media (max-width: 479px) { ... }` — компактные мобильные телефоны
- **Некорректные медиазапросы** (не использовать в новом коде):
  - `@media (max-width: 1024px)`, `@media (max-width: 768px)`, `@media (max-width: 480px)`, `@media (max-width: 991px)` — неправильные значения пикселей, не соответствующие сетке проекта.
  - Любые `min-width` запросы (если нет крайней технической необходимости).
- Использовать существующие токены: цвета, радиусы, тени, отступы из `variables.css`.
- Не использовать `!important`, если нет технически неизбежной причины.
- Не завышать специфичность селекторов и не строить длинные цепочки.
- Комментарий в начале нового CSS-файла должен кратко описывать назначение файла.

Рекомендуемый порядок CSS-свойств внутри правила:

1. Positioning
2. Box model
3. Typography
4. Visual
5. Interaction/animation

## 5. JavaScript-правила

- Использовать ES Modules и `type="module"`.
- Один переиспользуемый модуль должен экспортировать явную функцию инициализации: `initFeatureName()`.
- Перед запуском модуля проверять наличие нужного DOM-контракта на странице.
- Модуль не должен падать, если нужного блока нет в HTML.
- DOM-связи оформлять через понятные классы и `data-*` атрибуты.
- Не добавлять новые глобальные переменные и функции. Исключение - только совместимость с уже существующим legacy-кодом, если задача этого требует.
- Для новых фич не использовать jQuery и файлы из `js/legacy`.
- Новые библиотеки не добавлять без явной причины. Сначала проверить, решается ли задача существующим HTML/CSS/Vanilla JS.
- Комментарий в начале нового JS-файла должен кратко описывать назначение файла.

Типовой модуль:

```js
/*
 * Назначение: Логика блока избранного
 */

export function initFavorites() {
  const root = document.querySelector(".favorites");

  if (!root) {
    return;
  }

  // Логика блока
}
```

Типовая страничная точка входа:

```js
/*
 * Назначение: Точка входа страницы избранного
 */

import { initStickyHeader } from "../modules/sticky-header.js";
import { initMobileMenu } from "../modules/mobile-menu.js";
import { initCatalogModal } from "../modules/catalog-modal.js";
import { initFavorites } from "./favorites/favorites.js";

document.addEventListener("DOMContentLoaded", () => {
  if (document.querySelector(".header")) {
    initStickyHeader();
  }

  if (document.getElementById("burger-btn")) {
    initMobileMenu();
  }

  if (document.getElementById("catalog-btn")) {
    initCatalogModal();
  }

  initFavorites();
});
```

## 6. Документация для новых фич

Каждая новая фича, страница с собственной логикой или переиспользуемый компонент должны получить отдельный Markdown-файл в `documentation`.

Имя файла - короткое и понятное, в kebab-case:

```text
documentation/favorites-page.md
documentation/favorites-widget.md
documentation/checkout-steps.md
```

Документация должна содержать:

- Назначение фичи или компонента.
- Список связанных файлов с относительными путями.
- HTML-контракт: основные блоки, обязательные элементы, `data-*` атрибуты.
- CSS-контракт: ключевые классы, модификаторы, состояния.
- JS-контракт: точка входа, функция инициализации, события, зависимости.
- Правила адаптива и интерактивных состояний.
- Ограничения: что нельзя менять или на что завязана логика.

Ссылки в документации писать только относительными путями текущего проекта, например:

```text
css/modules/product-card.css
js/modules/product-card.js
documentation/product-card.md
```

Не использовать абсолютные локальные ссылки и ссылки на старые миграционные папки.

## 7. Чеклист перед завершением задачи

Перед финальным ответом по новой странице, компоненту или фиче проверить:

- HTML-файл лежит в корне, если это новая страница.
- CSS подключен в порядке: `custom-normalize.css`, `global.css`, страничный CSS.
- Новые общие стили не попали в страничный файл, а страничные стили не попали в `global.css`.
- JS подключен как `type="module"`, если это современная логика.
- Инициализация JS защищена проверками DOM.
- Изображения, иконки и шрифты лежат в `assets`.
- Для новой фичи создан `.md` файл в `documentation`.
- В новом коде нет подключений к старым миграционным папкам.
- Страница проверена минимум на desktop, tablet и mobile ширинах.
- Все изображения (кроме тех, что на первом экране/above-the-fold) имеют атрибут `loading="lazy"`, а также явные `width` и `height` для оптимизации скорости загрузки и предотвращения сдвигов макета (Layout Shift / CLS).
- Каждая HTML-страница содержит уникальный, информативный тег `<meta name="description" content="..." />` в секции `<head>` для лучшей индексации и SEO-оптимизации.
